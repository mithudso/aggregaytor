# Code reviewer context

## How to use this context

Use this file as a **practical code-review reference** when reviewing pull requests, auditing a codebase, or deciding whether a change should be approved, requested-changes, or deferred. Treat **Google Engineering Practices** as the source of truth for reviewer mindset, standards, and comment quality; **GitHub Docs** as the source of truth for pull-request review mechanics; and **OWASP** as the source of truth for security-focused review coverage and secure-coding checklist areas ([Google review overview](https://google.github.io/eng-practices/review/), [GitHub about pull request reviews](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/reviewing-changes-in-pull-requests/about-pull-request-reviews), [OWASP Code Review Guide project](https://owasp.org/www-project-code-review-guide/)).

**Version note:** this file is based on the current Google Engineering Practices pages and current GitHub Docs pages as accessed on **2026-05-10**. The supplied GitHub review URLs have moved, so this file cites the current official GitHub Docs paths for pull-request review pages. For OWASP, the official **Code Review Guide v2.0 (2017)** PDF and **Secure Coding Practices Quick Reference Guide v2.0.1 (2022)** are used because those are the current official guide artifacts linked from the project pages, even though the secure-coding quick reference project is archived ([OWASP Code Review Guide PDF](https://owasp.org/www-project-code-review-guide/assets/OWASP_Code_Review_Guide_v2.pdf), [OWASP Secure Coding Practices project page](https://owasp.org/www-project-secure-coding-practices-quick-reference-guide/)).

## Quick review rules

1. Approve a change once it **definitely improves overall code health**, even if it is not perfect; do not block on polish alone, but do not allow changes that worsen code health except in true emergencies ([Google standard](https://google.github.io/eng-practices/review/reviewer/standard.html)).
2. Start with the **purpose and high-level design** of the change before line comments; reject quickly if the change should not exist or if the main design is wrong ([Google navigate](https://google.github.io/eng-practices/review/reviewer/navigate.html)).
3. Review for **design, functionality, complexity, tests, naming, comments, style, and documentation**, not just syntax or style nits ([Google review overview](https://google.github.io/eng-practices/review/), [Google what to look for](https://google.github.io/eng-practices/review/reviewer/looking-for.html)).
4. Review **every line you are responsible for**, and pull in broader file or system context when the diff alone is insufficient ([Google what to look for](https://google.github.io/eng-practices/review/reviewer/looking-for.html)).
5. Be **kind, specific, and explicit about why** a change is needed; comment on the code, not the developer, and label non-blocking comments accordingly ([Google comments](https://google.github.io/eng-practices/review/reviewer/comments.html)).
6. Respond **quickly**: Google’s guideline is that one business day is the maximum response time, with fast responses prioritized over perfect uninterrupted review throughput ([Google speed](https://google.github.io/eng-practices/review/reviewer/speed.html)).
7. Prefer **small, reviewable PRs**; if a change is too large, ask for it to be split or send high-level design feedback first so the author is not blocked waiting for complete line review ([Google speed](https://google.github.io/eng-practices/review/reviewer/speed.html), [Google navigate](https://google.github.io/eng-practices/review/reviewer/navigate.html)).
8. Use GitHub review states deliberately: **Comment** for non-blocking feedback, **Approve** for merge-ready changes, and **Request changes** for issues that must be fixed before merge ([GitHub about pull request reviews](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/reviewing-changes-in-pull-requests/about-pull-request-reviews), [GitHub reviewing proposed changes](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/reviewing-changes-in-pull-requests/reviewing-proposed-changes-in-a-pull-request)).
9. Always run a **security sweep** on data handling, trust boundaries, authentication, session handling, access control, output encoding, logging, and configuration, even when the main review is not security-specific ([OWASP Code Review Guide PDF](https://owasp.org/www-project-code-review-guide/assets/OWASP_Code_Review_Guide_v2.pdf), [OWASP Secure Coding Practices v2.0.1 PDF](https://github.com/OWASP/secure-coding-practices-quick-reference-guide/releases/download/v2.0.1/OWASP_SCP_Quick_Reference_Guide.en-US.pdf)).

## Review workflow

1. **Understand intent and scope.** Read the change description first and determine whether the change makes sense for the system at all; if not, respond immediately and courteously with the alternative direction ([Google navigate](https://google.github.io/eng-practices/review/reviewer/navigate.html)).
2. **Check the main design first.** Review the most important files or the architectural center of the change before spending time on peripheral details, because major design problems can invalidate many smaller comments ([Google navigate](https://google.github.io/eng-practices/review/reviewer/navigate.html)).
3. **Review the rest in a deliberate order.** Google recommends an appropriate sequence after the main files, and notes that tests-first review can sometimes clarify intended behavior before reading the implementation ([Google navigate](https://google.github.io/eng-practices/review/reviewer/navigate.html)).
4. **Inspect behavior, edge cases, and risk.** Specifically consider user-facing behavior, concurrency, race/deadlock risk, unnecessary complexity, and over-engineering for speculative futures ([Google what to look for](https://google.github.io/eng-practices/review/reviewer/looking-for.html)).
5. **Verify tests and documentation.** Ask for unit, integration, or end-to-end tests as appropriate, and require documentation updates if the change affects build, test, usage, release, deletion, or deprecation flows ([Google what to look for](https://google.github.io/eng-practices/review/reviewer/looking-for.html)).
6. **Run the security checklist.** OWASP frames secure code review as a manual practice integrated into the secure SDLC and recommends risk-based review informed by threat modeling and common vulnerability classes ([OWASP Code Review Guide project](https://owasp.org/www-project-code-review-guide/), [OWASP Code Review Guide PDF](https://owasp.org/www-project-code-review-guide/assets/OWASP_Code_Review_Guide_v2.pdf)).
7. **Submit the right GitHub review state.** While reviewing, leave line comments, optional suggestions, and summary comments; use pending comments and viewed markers to manage the review; then submit Comment, Approve, or Request changes ([GitHub reviewing proposed changes](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/reviewing-changes-in-pull-requests/reviewing-proposed-changes-in-a-pull-request)).
8. **Resolve disagreement without drift.** If pushback arises, reconsider whether the author is right; otherwise explain the code-health rationale, escalate when needed, and avoid “clean it up later” as a default escape hatch for new complexity ([Google pushback](https://google.github.io/eng-practices/review/reviewer/pushback.html), [Google standard](https://google.github.io/eng-practices/review/reviewer/standard.html)).

## Code review goals and reviewer mindset

- Google’s core review goal is **improving overall code health over time**, not demanding perfection in every patch ([Google standard](https://google.github.io/eng-practices/review/reviewer/standard.html)).
- Reviewers are expected to balance two truths at once: developers must make progress, and each accepted change must not degrade maintainability, readability, or consistency of the system ([Google standard](https://google.github.io/eng-practices/review/reviewer/standard.html)).
- Technical facts and data outrank opinion. Style-guide requirements are binding; style points outside the guide become preference or consistency questions rather than merge blockers ([Google standard](https://google.github.io/eng-practices/review/reviewer/standard.html)).
- Code review is also a mentoring surface. Educational feedback is encouraged, but purely educational comments should be clearly marked as non-blocking so they do not stall forward progress ([Google standard](https://google.github.io/eng-practices/review/reviewer/standard.html)).
- OWASP adds a complementary security lens: secure code review is valuable because manual review still finds issues that automated scanners miss, and it should be part of the secure development lifecycle rather than a last-minute add-on ([OWASP Code Review Guide project](https://owasp.org/www-project-code-review-guide/), [OWASP Code Review Guide PDF](https://owasp.org/www-project-code-review-guide/assets/OWASP_Code_Review_Guide_v2.pdf)).

## What to look for in a review

### Core non-security review areas

- Review the **overall design** first: whether the change belongs here, integrates well with the system, and is a good time to add this functionality ([Google what to look for](https://google.github.io/eng-practices/review/reviewer/looking-for.html)).
- Review **functionality** from both end-user and future-developer perspectives, including edge cases and behavior that may only be obvious if you run the code or ask for a demo, especially for UI changes ([Google what to look for](https://google.github.io/eng-practices/review/reviewer/looking-for.html)).
- Look for **parallel-programming risk** such as race conditions and deadlocks; Google explicitly calls concurrency review especially important because these issues are hard to catch by execution alone ([Google what to look for](https://google.github.io/eng-practices/review/reviewer/looking-for.html)).
- Check for **unnecessary complexity** and over-engineering. Reviewers should push authors toward solving the actual current problem, not speculative future ones ([Google what to look for](https://google.github.io/eng-practices/review/reviewer/looking-for.html)).
- Treat **tests as first-class code**: they should fail for real breakage, avoid false positives, make useful assertions, and stay maintainable ([Google what to look for](https://google.github.io/eng-practices/review/reviewer/looking-for.html)).
- Require good **names**, useful **comments that explain why**, and updated **documentation** for changed build/test/use/release flows ([Google what to look for](https://google.github.io/eng-practices/review/reviewer/looking-for.html)).

### Security-focused review areas

- OWASP’s secure-coding checklist organizes high-value review coverage into **input validation, output encoding, authentication and password management, session management, access control, cryptographic practices, error handling and logging, data protection, communication security, system configuration, database security, file management, memory management, and general coding practices** ([OWASP Secure Coding Practices v2.0.1 PDF](https://github.com/OWASP/secure-coding-practices-quick-reference-guide/releases/download/v2.0.1/OWASP_SCP_Quick_Reference_Guide.en-US.pdf)).
- The OWASP quick reference explicitly recommends validating all untrusted input on a trusted system, rejecting validation failures, using contextual output encoding, centralizing authentication and authorization controls, using framework/session primitives correctly, avoiding sensitive data disclosure in errors, and keeping systems patched and securely configured ([OWASP Secure Coding Practices v2.0.1 PDF](https://github.com/OWASP/secure-coding-practices-quick-reference-guide/releases/download/v2.0.1/OWASP_SCP_Quick_Reference_Guide.en-US.pdf)).
- The OWASP Code Review Guide frames secure review as more than bug-spotting: it includes threat modeling, review methodology, code crawling, and targeted vulnerability review such as injection, broken authentication/session management, XSS, insecure direct object references, security misconfiguration, sensitive data exposure, missing function-level access control, CSRF, vulnerable components, and unvalidated redirects/forwards ([OWASP Code Review Guide PDF](https://owasp.org/www-project-code-review-guide/assets/OWASP_Code_Review_Guide_v2.pdf)).

## Writing effective review comments

- Be **courteous and respectful** and comment on the code rather than the developer; Google explicitly recommends phrasing comments so that critique lands on the implementation, not the person ([Google comments](https://google.github.io/eng-practices/review/reviewer/comments.html)).
- Explain **why** a requested change matters when the rationale is not already obvious; reviewers should make the code-health, maintainability, or user-impact reason clear ([Google comments](https://google.github.io/eng-practices/review/reviewer/comments.html)).
- Balance pointing out the problem with prescribing the exact solution. The author is responsible for fixing the CL, but concrete suggestions or code can still be helpful when they speed toward the best CL ([Google comments](https://google.github.io/eng-practices/review/reviewer/comments.html)).
- Label comment strength when useful: Google explicitly suggests prefixes such as **Nit**, **Optional/Consider**, and **FYI** so authors can tell required fixes from informational feedback ([Google comments](https://google.github.io/eng-practices/review/reviewer/comments.html)).
- When you ask for explanation because code is hard to understand, the usual correct outcome is clearer code or code comments that help future readers; review-tool-only explanations are not sufficient documentation for future maintainers in most cases ([Google comments](https://google.github.io/eng-practices/review/reviewer/comments.html)).
- Good reviews also call out **what is done well**, because reinforcement is part of mentoring and code-health culture ([Google comments](https://google.github.io/eng-practices/review/reviewer/comments.html), [Google what to look for](https://google.github.io/eng-practices/review/reviewer/looking-for.html)).

## Balancing quality, speed, and scope

- Google optimizes for **team velocity**, not individual reviewer convenience, so response time matters materially to delivery speed and code health ([Google speed](https://google.github.io/eng-practices/review/reviewer/speed.html)).
- The reviewer guideline is to respond within **one business day at most**, unless the reviewer is in the middle of focused work and waits for a natural break point ([Google speed](https://google.github.io/eng-practices/review/reviewer/speed.html)).
- Fast responses matter more than uninterrupted end-to-end completion time because quick back-and-forth reduces author frustration and review latency ([Google speed](https://google.github.io/eng-practices/review/reviewer/speed.html)).
- **LGTM with comments** is acceptable when remaining items are minor, clearly optional, or certain to be handled correctly by the author; the reviewer should make that intent explicit ([Google speed](https://google.github.io/eng-practices/review/reviewer/speed.html)).
- If a PR is too large, ask for it to be **split into smaller changes**, or at minimum provide high-level design comments quickly so the author can keep moving ([Google speed](https://google.github.io/eng-practices/review/reviewer/speed.html)).

## GitHub pull request review mechanics

- GitHub review states are **Comment**, **Approve**, and **Request changes**; reviews can include line comments, suggestions, and summary comments, and resolved conversation threads can be used to track addressed feedback ([GitHub about pull request reviews](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/reviewing-changes-in-pull-requests/about-pull-request-reviews)).
- GitHub recommends reviewing **one file at a time**, leaving comments on specific changes, and marking reviewed files as **Viewed** so progress is visible and the file collapses until changed again ([GitHub reviewing proposed changes](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/reviewing-changes-in-pull-requests/reviewing-proposed-changes-in-a-pull-request)).
- Pending comments remain visible only to the reviewer until submission, and a pending review can be abandoned before submission ([GitHub reviewing proposed changes](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/reviewing-changes-in-pull-requests/reviewing-proposed-changes-in-a-pull-request)).
- GitHub’s **Request changes** state is informational unless protected branches or rulesets require pull-request reviews; reviewers with sufficient repository permissions can block merge under those protections ([GitHub reviewing proposed changes](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/reviewing-changes-in-pull-requests/reviewing-proposed-changes-in-a-pull-request)).
- Pull-request authors **cannot approve their own pull requests** on GitHub ([GitHub reviewing proposed changes](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/reviewing-changes-in-pull-requests/reviewing-proposed-changes-in-a-pull-request)).
- **CODEOWNERS** can automatically request reviewers for owned files, and branch protection or rulesets can require code-owner approval before merge; CODEOWNERS files must be placed on the base branch and follow GitHub’s CODEOWNERS syntax constraints ([GitHub about code owners](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners)).

## Code review standards and best practices

### Review standard for accepting changes

- The approval threshold is **“definitely improves overall code health”**, not “perfect” ([Google standard](https://google.github.io/eng-practices/review/reviewer/standard.html)).
- A change that introduces known maintainability decline, unjustified complexity, or quality regression should not be approved outside emergencies ([Google standard](https://google.github.io/eng-practices/review/reviewer/standard.html)).

### Reviewer conduct and tone

- Be respectful, clear, and constructive; when disagreement exists, stay polite and keep arguing from code health and facts rather than personal preference ([Google comments](https://google.github.io/eng-practices/review/reviewer/comments.html), [Google pushback](https://google.github.io/eng-practices/review/reviewer/pushback.html)).
- Reconsider when the author’s argument is better; reviewers are not automatically right just because they review ([Google pushback](https://google.github.io/eng-practices/review/reviewer/pushback.html)).

### Comment quality

- Comments should say **what is wrong, why it matters, and how strongly the reviewer feels**; direct fixes are helpful when they shorten the path to the best result ([Google comments](https://google.github.io/eng-practices/review/reviewer/comments.html)).
- If code is too hard to understand, ask for clarification or simplification rather than silently guessing its intent ([Google what to look for](https://google.github.io/eng-practices/review/reviewer/looking-for.html)).

### Review scope control and PR sizing

- Prefer PRs that are small enough to review thoughtfully; large CLs should be split where possible ([Google speed](https://google.github.io/eng-practices/review/reviewer/speed.html)).
- Keep major style-only changes separate from functional changes so the review remains understandable and rollback-safe ([Google what to look for](https://google.github.io/eng-practices/review/reviewer/looking-for.html)).

### Test and documentation expectations

- Production changes should generally bring their tests in the same change, unless handling an emergency ([Google what to look for](https://google.github.io/eng-practices/review/reviewer/looking-for.html)).
- Documentation changes are required when the change alters how users build, test, use, release, remove, or deprecate the code ([Google what to look for](https://google.github.io/eng-practices/review/reviewer/looking-for.html)).

### Security review discipline

- Security review should not be postponed just because automated tooling exists; OWASP explicitly treats manual secure code review as a necessary SDLC practice ([OWASP Code Review Guide project](https://owasp.org/www-project-code-review-guide/), [OWASP Code Review Guide PDF](https://owasp.org/www-project-code-review-guide/assets/OWASP_Code_Review_Guide_v2.pdf)).
- Use the OWASP checklist areas as a minimum review frame for authentication, sessions, authorization, encoding, secrets, error/logging behavior, and configuration ([OWASP Secure Coding Practices v2.0.1 PDF](https://github.com/OWASP/secure-coding-practices-quick-reference-guide/releases/download/v2.0.1/OWASP_SCP_Quick_Reference_Guide.en-US.pdf)).

### Maintainability and long-term system health

- Favor simplification over speculative flexibility and insist on fixing newly introduced complexity now, not “later,” unless there is a real emergency ([Google what to look for](https://google.github.io/eng-practices/review/reviewer/looking-for.html), [Google pushback](https://google.github.io/eng-practices/review/reviewer/pushback.html)).
- When existing surrounding problems are discovered but cannot be fixed immediately, Google recommends filing a bug and optionally leaving a TODO tied to that bug rather than pretending the cleanup will just happen someday ([Google pushback](https://google.github.io/eng-practices/review/reviewer/pushback.html)).

### When to approve, comment, or request changes

- **Approve** when the change is merge-ready and clearly improves code health, even if minor non-blocking improvements remain ([Google standard](https://google.github.io/eng-practices/review/reviewer/standard.html), [GitHub about pull request reviews](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/reviewing-changes-in-pull-requests/about-pull-request-reviews)).
- Use **Comment** when feedback is informational, optional, or not a merge gate ([GitHub about pull request reviews](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/reviewing-changes-in-pull-requests/about-pull-request-reviews)).
- Use **Request changes** when issues must be fixed before merge and repository policy treats such reviews as merge-blocking or culturally mandatory ([GitHub reviewing proposed changes](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/reviewing-changes-in-pull-requests/reviewing-proposed-changes-in-a-pull-request)).

## Known ambiguities / scope notes

- Google’s reviewer guide is **process- and philosophy-heavy**, not language-specific. It gives strong standards for review behavior and acceptance thresholds, but it does not replace language/framework-specific best-practice docs ([Google review overview](https://google.github.io/eng-practices/review/)).
- GitHub Docs describe **workflow mechanics** and repository controls, not your team’s substantive quality bar. The platform can express reviews, but it does not decide whether a codebase has improved ([GitHub about pull request reviews](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/reviewing-changes-in-pull-requests/about-pull-request-reviews)).
- The OWASP **Code Review Guide v2.0** is still official but old enough that some vulnerability taxonomy and examples reflect the OWASP 2013 Top 10 era; use it for structured security review coverage, not as the only source for contemporary exploit taxonomy ([OWASP Code Review Guide project](https://owasp.org/www-project-code-review-guide/), [OWASP Code Review Guide PDF](https://owasp.org/www-project-code-review-guide/assets/OWASP_Code_Review_Guide_v2.pdf)).
- The OWASP **Secure Coding Practices Quick Reference Guide** project page is archived, but the official stable English **v2.0.1** PDF remains published and is still useful as a checklist source ([OWASP Secure Coding Practices project page](https://owasp.org/www-project-secure-coding-practices-quick-reference-guide/), [OWASP Secure Coding Practices v2.0.1 PDF](https://github.com/OWASP/secure-coding-practices-quick-reference-guide/releases/download/v2.0.1/OWASP_SCP_Quick_Reference_Guide.en-US.pdf)).
- The GitHub URLs supplied in the task for pull-request review pages were legacy paths that now return 404; this file cites the current official GitHub Docs URLs instead.
