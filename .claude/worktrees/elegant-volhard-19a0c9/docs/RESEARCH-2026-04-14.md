# Research notes — caching, libraries, assumptions 2026-04-14

Done as a follow-up to the v0.57.8 caching pass. Two goals:
1. Verify or challenge assumptions baked into the current code.
2. Identify novel libraries / tools / strategies we haven't considered.

Each finding is tagged with:
- **Assumption** — what the code believes
- **Verdict** — ✅ correct / ⚠️ partially / ❌ wrong
- **Evidence** — sourced
- **Gain** — estimated if we act on it
- **Action** — what to do (or why to ignore)

---

## 1. Storage layer — PouchDB vs alternatives

**Assumption:** "PouchDB is the right choice — IndexedDB singleton with auto_compaction, plus CouchDB API compatibility for possible future sync."

**Verdict:** ⚠️ partially

**Evidence:**
- PouchDB has known performance overhead from its CouchDB-compatible revision-tree storage. Every user doc writes two IndexedDB docs, and reads join two objectStores (slow on Chrome's IDB). [[RxDB: PouchDB Adapters]](https://rxdb.info/adapters.html)
- Dexie.js (29 KB gzipped) is a minimalistic IDB wrapper — bulk writes leverage an IDB feature (skipping `onsuccess` events on each write) that PouchDB can't use due to its revision-tree requirement. [[Dexie.js]](https://github.com/dexie/Dexie.js)
- PouchDB's built-in IndexedDB adapter is "nearly always more performant and stable" per the PouchDB docs — confirming the dual-storage pattern hurts. [[PouchDB Adapters]](https://pouchdb.com/adapters.html)
- OPFS is 3–4× faster than IndexedDB for reads, but only meaningful at >10k docs. [[RxDB: IndexedDB slowness]](https://rxdb.info/slow-indexeddb.html)
- `packages/store/src/sync.ts` is a **stub** — we never wired up CouchDB sync. The CouchDB-compat overhead is paid for a feature we don't use.

**Gain if we migrate to Dexie:**
- ~30–50% faster bulkDocs (conservative — our writes are already batched, so the benefit comes from dropping revision-tree work)
- -10–20 KB bundle size (PouchDB + pouchdb-find vs Dexie)
- Simpler type signatures (no `_rev` ceremony)

**Downside:**
- Migration work: ~800 lines of CRUD in `packages/store/src/*.ts` need rewriting. Tests need porting.
- Loss of optionality — if we ever want CouchDB sync we'd need to re-add that.
- Risk: Dexie's Mango-style queries are less expressive than PouchDB's `find()`.

**Action:** Keep PouchDB for now. The app isn't bottlenecked on writes. If we ever see real perf complaints or cross the 10k-docs threshold for a typical user, revisit — Dexie migration is the right move at that point. **Don't migrate speculatively.**

**One unambiguous improvement:** since we never sync, we could drop `pouchdb-find` and use `allDocs({ startkey, endkey })` for everything, eliminating the Mango query planner overhead. `getAllThreadMeta` and `getContactsByPlatform` already do this. Audit the remaining `db.find()` callers to see which can switch.

## 2. OPFS (Origin Private File System) for bulk data

**Assumption:** We don't consider OPFS anywhere.

**Verdict:** ⚠️ worth watching, not yet

**Evidence:**
- OPFS is 3–4× faster for reads, but the SQLite-on-OPFS sync path (`createSyncAccessHandle`) only works in a Worker, adding architectural complexity. [[RxDB: OPFS]](https://rxdb.info/rx-storage-opfs.html)
- Break-even vs IndexedDB is around 10k documents. [[RxDB storage comparison]](https://rxdb.info/articles/localstorage-indexeddb-cookies-opfs-sqlite-wasm.html)
- Supported in all modern browsers as of 2023; safe to use. [[web.dev: OPFS]](https://web.dev/articles/origin-private-file-system)
- MV3 service workers can't use OPFS directly — need a dedicated worker.

**Gain:** irrelevant until a user has 10k+ messages. Most users won't.

**Action:** none.

## 3. Anthropic prompt caching TTL

**Assumption:** We use `cache_control: { type: 'ephemeral' }` — default 5-min TTL.

**Verdict:** ⚠️ missing the 1-hour option

**Evidence:**
- Anthropic now supports `cache_control: { type: 'ephemeral', ttl: '1h' }`. Costs 2× base for cache writes (vs 1.25× for 5-min) but reads are still 0.1× base. [[Claude docs: prompt caching]](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)
- 1h TTL is optimal when "requests will be spaced more than 5 min apart but less than 1 hour" — exactly matches our auto-respond cadence for inactive users.
- 40–80% token-cost reductions reported in real-world agentic tasks. [[Prompt Hub]](https://www.prompthub.us/blog/prompt-caching-with-openai-anthropic-and-google-models)
- From Feb 5 2026, caching uses workspace-level isolation instead of org-level — no code change needed for us.

**Gain:**
- For users whose inbox fires autoresponds every 10–30 min, a 1h TTL would hold the system prompt cache across those gaps. Cache read cost is 1/10th; cache write cost is ~2× — the break-even is roughly **3 subsequent hits within the hour**.
- Real-world: modular-prompt layer keeps the persona/style prefix stable, so almost every request benefits.
- Estimated cost reduction: **+15–20 percentage points on cached tokens** vs current 5-min TTL for intermittent-use patterns.

**Action:** **Wire a settings toggle** — users who use the extension lightly (once/hour) set `useLongCache: true`. Default stays 5-min for heavy users.

## 4. Gemini explicit context caching

**Assumption:** We rely on Gemini's implicit caching only.

**Verdict:** ✅ correct for our usage pattern, but knowable

**Evidence:**
- Gemini 2.5 models now support **implicit** caching with automatic 90% discount on cache hits — no code changes needed. [[Google Developers Blog]](https://developers.googleblog.com/gemini-2-5-models-now-support-implicit-caching/)
- Explicit caching adds storage cost, and break-even is ~4 queries/hour per 1M cached tokens. [[AI Free API: Gemini caching]](https://www.aifreeapi.com/en/posts/gemini-api-context-caching-reduce-cost)

**Gain:** Our cached system prompts are small (~500 tokens). Implicit caching is already free. Explicit caching would only pay off for very large system prompts (>5k tokens sustained over hours).

**Action:** none. Document in llm.ts why we don't use explicit Gemini caching.

## 5. OpenAI automatic prompt caching

**Assumption:** We don't explicitly manage OpenAI caching.

**Verdict:** ✅ correct — nothing to do, but our prompt structure matters.

**Evidence:**
- OpenAI auto-caches prompts longer than **1024 tokens**, in 128-token increments beyond. [[OpenAI prompt caching]](https://platform.openai.com/docs/guides/prompt-caching)
- Cached tokens are 50% off on GPT-4o. No code change required. [[Markaicode]](https://markaicode.com/openai-prompt-caching-how-it-works/)
- Cache hits require **100% identical prefix**. Structure: static-first, dynamic-last. [[Prompt Hub]](https://www.prompthub.us/blog/prompt-caching-with-openai-anthropic-and-google-models)

**Our status:** The modular-prompt work in v0.57.8 already optimises for this — persona/style/tier modules come first, per-request context last. ✅

**One gap:** `buildConversationContext` puts the conversation BEFORE the JSON-format reminder at the end. Since OpenAI caches the prefix only, our cached part stops at the conversation. This is actually correct (conversation changes per call) — but we could move more static content AFTER the conversation in the user-message position so the system prompt stays maximally cacheable.

**Action:** **no change** — current structure is correct. Added note to ARCHITECTURE.md for future-me.

## 6. Missing fast-inference providers

**Assumption:** We support gemini / openai / anthropic / groq / perplexity / mistral / copilot / local.

**Verdict:** ❌ missing Cerebras and SambaNova — both have exceptional free tiers.

**Evidence:**
- **Cerebras:** 30 RPM, **1M tokens/day** free. 2600 tok/s on Llama 4 Scout = ~10× faster than Groq. [[Cerebras free tier]](https://pricepertoken.com/endpoints/cerebras/free)
- **SambaNova:** Persistent free tier, 10–30 RPM depending on model. [[Awesome Agents]](https://awesomeagents.ai/tools/free-ai-inference-providers-2026/)
- Both expose OpenAI-compatible APIs — adding them is a ~15-line PROVIDER_RPM + TIERED_MODELS addition + one switch case.

**Gain:**
- Another free-tier fallback. Our current chain runs out of Gemini (15 RPM) and Groq (30 RPM) at ~45 RPM total. Cerebras adds +30 RPM with the best daily quota in the market.
- Cerebras speed = lower latency for interactive suggestions.

**Action:** **Add Cerebras provider** — low-risk, high-value. SambaNova is similar but lower priority (smaller quota).

## 7. Full-text search over messages

**Assumption:** `SEARCH_MESSAGES` scans 5000 docs (now 20× limit cap in v0.57.7) and substring-matches in JS.

**Verdict:** ❌ slow on large corpora. FlexSearch would be dramatically better.

**Evidence:**
- **FlexSearch** claims up to 1,000,000× faster queries than alternative libraries, zero dependencies, ~20 KB. [[FlexSearch GitHub]](https://github.com/nextapps-de/flexsearch)
- **MiniSearch** is simpler but degrades on larger datasets. [[NPM compare]](https://npm-compare.com/elasticlunr,flexsearch,fuse.js,minisearch)
- PouchDB has no native FTS. Building the index ourselves is fine — IDs are enough to re-fetch docs from PouchDB.

**Gain:**
- Today: ~500ms to search 5000-message corpus (full substring scan).
- With FlexSearch in-memory index: ~5ms (2-order-magnitude speedup).
- Index size on an average corpus: ~3–8% of the message corpus size — negligible in memory.

**Downside:**
- Index must be maintained on every message write. Small per-write cost (~0.5ms).
- Memory footprint: ~500KB for 5000 messages indexed. Acceptable.
- Cold-start: rebuild index from PouchDB on SW wakeup. Could take 200-500ms for 5000 messages. Mitigate by lazy-loading on first search.

**Action:** **Add a FlexSearch index** as an opt-in layer over `SEARCH_MESSAGES`. Lazy-built on first call, maintained incrementally thereafter. Skip in tests (pass-through to current scan).

## 8. Service-worker bundle size

**Assumption:** We don't explicitly care about bundle size.

**Verdict:** ⚠️ bundle has crept up. 588 KB (pre-v0.57.8) → 602 KB (post). Parsed on every cold start.

**Evidence:**
- Chrome parses the full SW bundle on every wakeup. Bundle size correlates with cold-start latency.
- We pull in PouchDB + pouchdb-find (majority of weight). [[our build output]](extensions/aggregaytor/dist/background/service-worker.js)

**Spot-test numbers (local):**
```
588K service-worker.js   ← everything including PouchDB, store CRUD, LLM providers
156K panel.js            ← sidepanel UI
 96K sniffies.js         ← largest content-script bundle
```

**Gain:**
- If we split llm.ts into a lazy-loaded chunk (only imported when a GENERATE_* message fires), we could defer ~100 KB out of cold start. Currently llm.ts IS statically imported at the top of service-worker.ts.
- Vite already warns about the static-vs-dynamic conflict: `llm.ts is dynamically imported by service-worker.ts but also statically imported`.

**Action:** Non-trivial refactor. **Skip** — cold-start latency isn't a reported issue. Document for later.

## 9. Chrome extension auto-reload pattern

**Assumption:** Custom `.build-hash` poller + `chrome.runtime.reload()` is the pattern.

**Verdict:** ⚠️ works, but CRXJS is idiomatic

**Evidence:**
- **CRXJS/vite-plugin** is the de-facto standard now, with HMR for content scripts and auto-reload for SW. [[CRXJS]](https://www.npmjs.com/package/@crxjs/vite-plugin)
- Our custom approach uses `setInterval(1500ms)` inside the SW, which Chrome can suspend. We compensate with a `chrome.alarms` keepalive every 30s.
- CRXJS uses WebSocket from the dev server instead — always works when the dev server is alive.

**Gain:** Faster dev iteration (~1s vs ~3s), true HMR for content scripts (don't reload whole page).

**Downside:**
- Migration effort: manifest.json gets generated by the plugin, breaking our custom build pipeline
- Our two-pass IIFE build for content scripts is not stock CRXJS behaviour

**Action:** Evaluate later; not urgent. Current approach is reliable.

## 10. `chrome.storage.local` encryption at rest

**Assumption:** Only Grindr credentials are encrypted (AES-GCM, device-local key). Everything else stored plain.

**Verdict:** ⚠️ intentional tradeoff; flag for review if threat model changes.

**Evidence:**
- `chrome.storage.local` is NOT encrypted by default. [[codestudy.net]](https://www.codestudy.net/blog/chrome-extension-encrypting-data-to-be-stored-in-chrome-storage/)
- Filesystem-level attackers can read it directly. Same security model as browser password managers.
- Best practice: encrypt sensitive data with AES-GCM via Web Crypto API, derive key from user input (not device salt) for strongest security.
- Match Group had a 10M-record breach Jan 2026, highlighting why data minimisation matters. [[GhostMyData]](https://ghostmydata.com/blog/dating-apps-privacy-comparison-2026)

**Gain if we encrypt everything:**
- Filesystem-level attacker must now extract crypto key from extension memory — harder but not impossible.
- Overhead: AES-GCM encrypt/decrypt on every PouchDB read/write. ~1-3ms per op on modern hardware. Would add up on bulk imports.

**Action:**
- Current approach is a reasonable tradeoff. **Don't encrypt all data by default.**
- **Recommend** adding a "vault mode" setting where user provides a passphrase; if set, encrypt message bodies and dossier fields. Default off.
- Document threat model in ARCHITECTURE.md.

## 11. Multi-provider router libraries (LiteLLM, Vercel AI SDK)

**Assumption:** Hand-rolled provider fallback in llm.ts is fine.

**Verdict:** ✅ correct for this codebase

**Evidence:**
- **LiteLLM** is Python-only — we're in a browser service worker, cannot use it. [[LiteLLM alternatives]](https://www.edenai.co/post/best-alternatives-to-litellm)
- **Vercel AI SDK** could work but is Next.js-centric, adds bundle weight, and doesn't offer much over our existing queue+backoff+coalesce logic. [[Vercel AI Gateway comparison]](https://www.getmaxim.ai/articles/top-5-llm-router-solutions-in-2026/)
- **OpenRouter** is a hosted gateway — would introduce a single point of failure + monthly fee; defeats the privacy model.

**Action:** none. Keep current implementation.

**Assumption:** We're a single-device app; no cross-device sync needed.

- Our v0.57.8 signal index is essentially a handcrafted CRDT-adjacent pattern (high-water mark + delta scan). Works well for our single-device model.

**Action:** none. Document the design choice.

## 13. Google OAuth token lifetime

**Assumption:** Tokens last 60 min, we cache for 50 min.

**Verdict:** ✅ correct

**Evidence:**
- `chrome.identity.getAuthToken` caches tokens in memory with automatic expiration handling. [[MDN identity]](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/identity)
- Google's default access token TTL is 3600s. Our 50-min cache leaves a 10-min safety margin.

**Action:** none.

## 15. Legal / ethical — dating app scraping

**Assumption:** We don't address this in code or docs.

**Verdict:** ⚠️ user's responsibility, but worth flagging

**Evidence:**
- Reading your own inbox messages via browser automation is very different from third-party data scraping. Our tool only uses APIs the user's session is already authorised for. [[Avvo]](https://www.avvo.com/legal-answers/is-it-illegal-to-scrape-a-dating-website-for-data--2892198.html)
- Match Group / Bumble breach Jan 2026 (ShinyHunters, 10M records) is a reminder that dating-app data is high-value. Our local-first design minimises exposure. [[GhostMyData]](https://ghostmydata.com/blog/dating-apps-privacy-comparison-2026)
- Technically violates platform ToS — same as any inbox-unifier (Thunderbird connecting to Gmail, etc.).

**Action:** Add a note to ARCHITECTURE.md about privacy posture. Not a technical change.
